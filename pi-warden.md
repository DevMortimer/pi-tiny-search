Copy this file to the root of your project as `pi-warden.md` and edit it. Every `#` heading below is one rule. The text
under a heading is what Jev reads when it judges a write or an edit. A `paths:` line right under a heading limits that rule
to matching files. Text above the first heading, like this paragraph, is ignored, so keep the intro heading-free.

Keep rules short and concrete. Say what a violation looks like. Jev is good at "must not contain X" and "every X needs a Y";
it is worse at taste ("code should be clean").

# No hardcoded secrets
Source code must not contain API keys, tokens, or connection URLs with credentials. They come from environment variables or
the credentials module. A test fixture with an obviously fake value such as `test-key` is fine.

# Comments explain why, not what
A comment states a reason, a constraint, a workaround, or a non-obvious invariant. A comment that restates what the next line
plainly does is a violation.

# Errors are not swallowed
A `catch` block must handle the error, report it, or re-raise it. An empty catch block, or one whose body is only a comment,
is a violation.

# No partial implementations
Implement features fully. A comment that says "for now", "simplified", or "later", or a stub body such as `throw new Error("not
implemented")`, is a violation. If a part genuinely cannot be done, say so in your reply instead of stubbing it.

# API request bodies are clean
paths: src/**
Request bodies sent to the Monid API must contain only fields defined in the TinyFish schema. Unknown fields cause HTTP 400.
Do not forward internal metadata, categorization tags, or eval-only fields into API payloads.

# Rate limits are handled, not ignored
paths: src/**
The client enforces 30 searches/minute and 150 fetches/minute locally. Upstream 429 responses must trigger exponential backoff,
not immediate retry. A `catch` that silently ignores a rate limit error is a violation.

# Tool descriptions are honest
The `description` and `promptSnippet` of a registered tool must accurately reflect what the tool does and what it returns. A
description that promises content the tool does not deliver is a violation.

# Redaction before any external surface
Any search query, URL, or result that appears in a steer, trace entry, status line, or notification must be safe to display. The
API key must never appear in error messages, logs, or trace entries.

# Config is additive
paths: src/**
New config keys get a default in `defaultConfig()`, a fallback in the config schema, and one line in `docs/configuration.md`.
Removing or renaming an existing key is a breaking change.

# Tests isolate machine state
paths: tests/**
Tests that call `keySituation()` or read credentials must temporarily move `auth.json` aside. The stored key always exists on
developer machines — a test that assumes it does not will pass in CI but fail locally (or vice versa).

# No tool or AI attribution
Commits and PR descriptions say what changed and why. No "Generated by", "Co-authored-by", or similar attribution lines from
tools or AI models.

# Do not bump version in a feature or fix commit
The version bump is the last commit on the PR. See "Version bumps and changelogs" in AGENTS.md.

# Do not run destructive commands that erase uncommitted work
`git reset --hard`, `git checkout -- .`, `git clean -fd`, and similar commands that discard untracked or uncommitted changes are
forbidden. These destroy work that has no backup. If a clean tree is needed, create a worktree instead or ask the user.
